# 数据源与地理标签

## 当前上游

- 主数据源：<https://zip.cm.edu.kg/all.json>
- TXT 回退：<https://zip.cm.edu.kg/all.txt>

这些是项目当前配置的公开资源端点。项目不是该资源库的所有者，不保证其长期可用、覆盖率、节点有效性或地理信息准确性。请求时应使用合理频率，遵守上游条款与服务约束。

## 为什么优先读取 JSON

结构化 JSON 的记录可包含：

- ip：候选地址；
- port：一个或多个端口；
- locations.region：上游给出的大洲/区域；
- locations.cca2：两位国家代码；
- locations.city：城市标签；
- locations.iata：机场/城市代码；
- locations.lat、locations.lon：坐标；
- 顶层 generated_at、list 等资源描述字段（字段以实时上游 schema 为准）。

软件直接沿用这些地理字段作分组。它们是数据提供方的分类元数据，不是 ProxyIP 服务器物理机房的独立证明。IP 可能是 Anycast、转发入口、隧道终点或被第三方标注的地址，显示城市不应解读为网络路由一定落在该城市。

## TXT 回退的限制

TXT 记录格式类似：

~~~text
103.102.228.113:443#NL
103.102.228.121:2053#NL
~~~

字段含义为 IP、端口和国家代码。TXT 并不提供完整城市数据；当 JSON 不可用而使用 TXT 时，城市应显示“城市未标注”或等价文案，不能通过猜测补齐。

## 规范化规则

- 一个 IP 拥有多个端口时，应展开成多个独立 IP:Port 节点。
- 对 IP 和端口做校验；非法项应跳过并在统计/日志中可追踪。
- 规范化后应去重。
- JSON/TXT 合并时，优先保留 JSON 提供的更完整地理字段。
- 国家代码、国家显示名和大洲标签必须有一致的测试。
- 缺少字段时使用明确的未知值，不把空值推导成确定事实。

## 缓存和刷新

资源读取成功时将解析后的目录写到 Electron userData 缓存。网络失败时可读取缓存，但界面必须标明“本机缓存”等状态，并尽量显示缓存时间/原始生成时间。不要把缓存结果伪装成刚获取的实时目录。

刷新资源和探测状态是不同动作：
- 刷新资源负责更新列表及地理信息；
- 测速负责验证当前候选 IP:Port 的本机连通性；
- 一个节点的探测成功不等于该节点永久可用。

## 数据源变更流程

如果上游端点或 JSON schema 变更：
1. 检查实际响应样例和更新时间。
2. 不要把大体积动态列表整个写死到源码。
3. 更新 src/catalog.cjs，保持对缺字段和格式错误的容错。
4. 为新的字段和异常样例增加固定的小型单元测试。
5. 更新本文件和 DEVELOPMENT-LOG-CN.md。
6. 如上游不可用，报告事实并保留缓存路径，不要擅自改用未经确认的来源。
